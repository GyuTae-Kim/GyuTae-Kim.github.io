서버가 멀쩡해도 몇 주씩 모르고 지나던 업무 실패까지 찾아냅니다

서비스 3개의 서버 구성요소 13곳과 송장 전송·알림톡 같은 실제 업무 결과를 함께 감시합니다. 서버 API와 사용자 PC 앱의 오류를 모아, 슬랙 알림에서 관리자 화면의 원인 확인으로 이어지는 운영 도구를 개발했습니다.

  • 0.5초 → 0.1초느린 조회 개선 직후 관측한 주문 서비스 DB 평균 응답
  • 6건감시 알림으로 찾아 원인을 고친 운영 문제
  • 13곳1분마다 확인하는 서버 구성요소
맡은 역할
감시 기준과 알림 흐름을 설계했습니다. 감시 프로그램과 서버 상태 화면, 업무 결과 확인, API 오류와 PC 앱 오류 수집, 이를 모아 보는 관리자 콘솔까지 직접 개발했습니다.
만들어낸 결과
서버 상태, 실제 업무 처리 결과, API·PC 앱 오류를 함께 살펴보는 감시 체계를 만들었습니다. 경보·복구 알림·정기 보고와 관리자 콘솔을 연결했고, 감시가 찾아낸 느린 조회와 송장·알림톡 연동 문제 6건의 원인을 고쳤습니다.
  1. 1서버 감시13곳을 정상, 성능 저하, 장애, 확인 불가로 판정
  2. 2업무 결과 확인요청이 접수됐는지가 아니라 실제로 처리됐는지로 판정
  3. 3알림과 보고3번 연속 실패하면 경보, 복구 때 한 번 더, 하루 두 번 정기 보고
  4. 4오류 수집서버 API 오류와 PC 앱 오류를 모아 같은 오류끼리 묶음

이 기술로 기대하는 변화

작은 팀의 운영 대응

담당자가 여러 관리 화면을 계속 지켜보는 대신 이상과 복구를 알림으로 확인해, 반복 점검 부담을 줄이고 원인 파악에 집중할 수 있습니다.

고객에게 닿기 전 문제 발견

서버가 정상이어도 배송 정보나 업무 알림이 누락되는 실패를 감지해, 고객 문의가 들어오기 전에 조치하는 데 도움을 줄 수 있습니다.

개선으로 이어지는 오류 기록

서버와 사용자 PC에서 발생한 오류를 묶어 반복되는 문제를 찾고, 수정 뒤의 상태를 비교할 수 있는 운영 근거를 남깁니다.

문제와 해결

  1. 문제서버가 정상이어도 송장 전송이나 알림톡 발송은 실패한 채 남을 수 있습니다.

    해결요청 접수와 실제 처리 결과를 구분해, 업무 실패와 끝나지 않은 실행도 감시에 연결했습니다.

  2. 문제관리자 분석 작업이나 첫 결과를 기다리는 상태가 실제 장애처럼 보였습니다.

    해결작업 출처를 구분하고 수집 대기·결과 미확인·확정 실패를 나눠, 대응이 필요한 이상을 알아볼 수 있게 했습니다.

  3. 문제장애 중에 수집 연결이 끊기면 그동안의 상태 이력이 비었습니다.

    해결관측을 임시 보관했다가 연결이 돌아오면 중복 없이 보내, 장애와 복구 흐름을 이어 볼 수 있게 했습니다.

  4. 문제서버가 늦거나 끊겼을 때 오류 전송을 기다리면 가구빌더 편집과 출력이 함께 멈춥니다.

    해결편집과 출력을 기다리게 하지 않고 오류를 따로 전송하며, 같은 오류의 반복 전송을 제한했습니다.

  5. 문제오류 메시지에 토큰이나 파일 경로가 섞여 들어올 수 있습니다.

    해결PC와 서버 양쪽에서 민감한 부분을 지운 첫 줄만 남기고, 도면 내용은 보내지 않습니다.

검증과 확인한 결과

  • 관리자 상태 화면·슬랙 보고·장애와 복구 이력을 대조했습니다.
  • 느린 조회 수정 직후 DB 평균 응답이 0.5초대에서 0.1초 안팎으로 변한 운영 그래프를 확인했습니다.
  • 송장·알림톡·DB 연결 등 감시 알림에서 원인을 추적해 조치한 6건을 기록했습니다.

감시가 찾아낸 실제 문제 6건

  1. 09.30

    감시를 켠 첫날, 주문 서비스 DB의 평균 응답이 0.5초 안팎으로 느렸고 관리 화면의 기간별 추이 조회가 평균 4~5초씩 걸리는 것이 잡혔습니다.

    조회를 고친 직후 DB 평균 응답이 0.1초 안팎으로 떨어졌습니다. 같은 원인이던 조회 17개도 같은 방식으로 고쳤습니다.

  2. 10.01

    배포 점검 작업이 DB 트랜잭션을 연 채 파일 저장소를 읽어, 연결을 10초 넘게 붙잡았습니다.

    DB 조회만 연결 안에서 하고, 파일 확인은 연결을 닫은 뒤 하게 했습니다.

  3. 10.06

    같은 순간 시작한 송장 전송 두 건이 함께 실패로 기록됐습니다.

    전송 충돌과 같은 송장의 중복 전송을 없앴습니다.

  4. 10.06

    배송 알림톡 4건의 발송 결과가 끝내 오지 않았습니다. 최근 120일을 점검하니 결과를 못 받은 메시지가 65건이었습니다.

    발송 뒤 결과가 없는 메시지를 1분마다 다시 조회해 맞추게 했습니다.

  5. 10.13

    주문 하나가 9월 초부터 6주 동안 송장 전체 전송 때마다 실패하고 있었습니다.

    이미 등록된 번호와 비교해 완료로 기록하게 고쳤습니다.

  6. 10.13

    가상계좌 입금 때 주문 완료 알림톡을 다시 보내다 거절됐습니다.

    주문할 때 이미 보낸 알림톡을 입금 때 다시 보내지 않게 했습니다.
