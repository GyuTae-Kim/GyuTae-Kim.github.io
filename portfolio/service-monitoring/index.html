감시가 찾아낸 실제 문제 6건

  1. 09.30

    감시를 켠 첫날, 주문 서비스 DB의 평균 응답이 0.5초 안팎으로 느렸고 관리 화면의 기간별 추이 조회가 평균 4~5초씩 걸리는 것이 잡혔습니다.

    조회를 고친 직후 DB 평균 응답이 0.1초 안팎으로 떨어졌습니다. 같은 원인이던 조회 17개도 같은 방식으로 고쳤습니다.

  2. 10.01

    배포 점검 작업이 DB 트랜잭션을 연 채 파일 저장소를 읽어, 연결을 10초 넘게 붙잡았습니다.

    DB 조회만 연결 안에서 하고, 파일 확인은 연결을 닫은 뒤 하게 했습니다.

  3. 10.06

    같은 순간 시작한 송장 전송 두 건이 함께 실패로 기록됐습니다.

    전송 충돌과 같은 송장의 중복 전송을 없앴습니다.자세히

  4. 10.06

    배송 알림톡 4건의 발송 결과가 끝내 오지 않았습니다. 최근 120일을 점검하니 결과를 못 받은 메시지가 65건이었습니다.

    발송 뒤 결과가 없는 메시지를 1분마다 다시 조회해 맞추게 했습니다.

  5. 10.13

    주문 하나가 9월 초부터 6주 동안 송장 전체 전송 때마다 실패하고 있었습니다.

    이미 등록된 번호와 비교해 완료로 기록하게 고쳤습니다.자세히

  6. 10.13

    가상계좌 입금 때 주문 완료 알림톡을 다시 보내다 거절됐습니다.

    주문할 때 이미 보낸 알림톡을 입금 때 다시 보내지 않게 했습니다.

맡은 역할
감시 기준과 알림 흐름을 설계했습니다. 감시 프로그램과 서버 상태 화면, 업무 결과 확인, API 오류와 PC 앱 오류 수집, 이를 모아 보는 관리자 콘솔까지 직접 개발했습니다.
  1. 1서버 감시13곳을 정상, 성능 저하, 장애, 확인 불가로 판정
  2. 2업무 결과 확인요청이 접수됐는지가 아니라 실제로 처리됐는지로 판정
  3. 3알림과 보고3번 연속 실패하면 경보, 복구 때 한 번 더, 하루 두 번 정기 보고
  4. 4오류 수집서버 API 오류와 PC 앱 오류를 모아 같은 오류끼리 묶음
자세히 · 문제와 해결, 화면

  1. 문제관리자가 직접 돌린 분석 작업이 오래 걸리자 서비스 지연 경보가 울렸습니다.

    해결작업 출처를 구분해 진단 작업은 경보 판정에서 뺐습니다.

  2. 문제새 감시 항목이 첫 결과를 기다리는 동안 실패처럼 보였습니다.

    해결수집 대기, 결과 미확인, 확정 실패를 나눠 표시했습니다.

  3. 문제장애 중에 수집 연결이 끊기면 그동안의 상태 이력이 비었습니다.

    해결최대 3일치 관측을 보관했다가 연결이 돌아오면 중복 없이 보냅니다.

  4. 문제서버가 늦거나 끊겼을 때 오류 전송을 기다리면 가구빌더 편집과 출력이 함께 멈춥니다.

    해결오류 지점에서는 메모리에 담기만 하고, 전송은 따로 5초 제한으로 보냅니다. 같은 오류는 1분에 한 번만 보냅니다.

  5. 문제오류 메시지에 토큰이나 파일 경로가 섞여 들어올 수 있습니다.

    해결PC와 서버 양쪽에서 민감한 부분을 지운 첫 줄만 남기고, 도면 내용은 보내지 않습니다.

  6. 문제자동 테스트가 일부러 낸 실패가 운영 오류 목록에 섞였습니다.

    해결테스트 실행 중에 난 오류는 보내지 않게 막았습니다.
